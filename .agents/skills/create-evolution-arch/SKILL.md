# Create Evolution Arch（人工交互）

## 何时使用

- 用户手动触发：为目标项目首次生成 `docs/arch.md`、体检已有架构文档，或修订已经过时的架构决策
- 项目需要把 PRD/goal 中的产品事实落到技术架构、部署边界、模块边界、请求路径与关键约束
- 需要用某个参考 `arch.md` 学习章节结构时：只参考结构、表达层次和覆盖面，**不得复制参考项目的技术事实**
- **禁止**被无人值守演化流程（Automations / evolution-* subagent）调用

## 生产姿态（全程强制）

`docs/arch.md` 描述的是**可上线生产系统**如何组成与演进，不是演示拓扑。

| 禁止出现在 arch 中的内容 | 正确做法 |
|--------------------------|----------|
| stub / mock 假服务 / 内存假后端作为正式组件 | 只画真实进程、真实外部依赖；测试双不进架构图 |
| 「临时 mock，上线前替换」作为架构决策 | 决策要么接真实集成，要么能力未就绪则不宣称、不挂生产入口 |
| MVP / demo 部署形态当目标态 | 可用「首版部署范围更小」，但组件与路径必须是生产级真实实现 |
| 假绿友好路径（永远成功的占位适配器） | 失败模式、降级、熔断须诚实；禁止「占位成功」 |

**例外（勿写入正式架构组件）**：`*_test` / fixture / 仅本地测试 harness 中的 mock —— 可在「测试策略」一笔带过，**不得**出现在系统架构图、请求路径、模块边界表里。

## 文档定位

`docs/arch.md` 是自我演化的**技术架构与关键决策源**，回答「系统如何组成、为何这样设计、哪些边界不能跨、如何部署和演进」。它不替代 PRD，不新增产品需求，不排里程碑。

| 文档 | 定位 | 本 skill 是否修改 |
|------|------|------------------|
| `docs/automate/goal.md` | 产品方向与边界 | 否，只读 |
| `docs/automate/prd.md` + `docs/automate/prd/*.md` | 功能真理源与验收标准 | 否，只读 |
| `docs/automate/plan.md` | 人工里程碑与顺序干预 | 否，只读 |
| `docs/automate/evolution-state.md` | 当前轮次、待办池、模块地图、项目 skill/rule 索引 | 否，只读 |
| `docs/arch.md` | 技术架构、部署形态、模块边界、关键决策 | 是 |

## 工作模式

| 模式 | 触发 | 输出 |
|------|------|------|
| 新建 | `docs/arch.md` 不存在 | 完整架构文档 |
| 体检 | `docs/arch.md` 已存在，用户要求检查 | 质量评分 + 漂移清单 + 修订建议 |
| 修订 | 用户确认要调整已有架构章节 | 最小范围修改 + 决策记录 |
| 迁移 | 架构内容散落在 README、PRD、设计文档 | 汇总到 `docs/arch.md`，源文档只在用户确认时改引用 |

## 提问纪律

- **一次只问一个问题**；能给选项就给选项（多选一优先，附推荐项）
- 提问前先读上下文：README、`docs/automate/goal.md`、`docs/automate/prd.md`、已有 `docs/arch.md`、关键配置文件、`git log -10`
- 用户提供参考架构文档时，先提炼其章节骨架，再结合目标项目事实重写
- 用户跳过问题 → 采用推荐默认值，并在产出中该处标注 `（待确认）`
- 写入前必须展示「变更摘要 + 将写入的章节预览 + 仍待确认项」，等待用户明确确认
- 发现用户想用 stub/mock「先跑通」→ **拒绝写入架构**，改为讨论真实依赖接入或缩小 In Scope

## 质量评分（100 分）

| 维度 | 分值 | 检查点 |
|------|-----:|--------|
| 架构定位清晰度 | 10 | 能说明系统形态、核心用户、部署环境、与 goal/prd 的关系 |
| 技术栈完整性 | 10 | 后端、前端、数据、缓存、队列、存储、协议、构建部署均有明确选型或待定标注 |
| 边界与模块划分 | 15 | 模块职责、进程边界、外部系统、禁止跨界点清楚 |
| 请求与数据路径 | 15 | 关键用户/API/后台任务/异步链路可追踪，且每跳为真实组件 |
| 部署与运维可落地 | 15 | 环境、配置、依赖、扩缩容、备份、观测、失败模式有说明 |
| 生产诚实性 | 15 | 无 stub/假服务/假绿路径；外部依赖标明契约与失败行为；无 MVP 玩具拓扑 |
| 决策可追溯性 | 10 | 关键取舍有原因、状态、影响范围；避免只列结论 |
| 安全与合规覆盖 | 10 | 认证、权限、审计、密钥、数据保护、合规要求与 PRD/goal 对齐 |

评分解释：

| 分数 | 结论 |
|------|------|
| 90-100 | 可作为 P1/P3 架构约束与设计评审稳定输入 |
| 80-89 | 可用，但有少量待确认或薄弱链路 |
| 70-79 | 能启动，但容易让实现阶段在边界/部署/数据路径上漂移 |
| <70 | 建议继续交互澄清，不写入正式 arch 或只写草案 |

**硬门槛**：架构图或请求路径含正式 stub/mock 假服务，或把 demo 拓扑当目标态 → 「生产诚实性」0 分，总分上限 69。

## 首次生成（arch.md 不存在）

1. 读项目事实源：
   - `README.md`
   - `docs/automate/goal.md`
   - `docs/automate/prd.md` 与必要分片
   - `docs/automate/evolution-state.md` 的模块地图（若存在）
   - 关键清单与配置：`package.json`、`go.mod`、`pyproject.toml`、`Cargo.toml`、`Makefile`、`docker-compose*`、`Dockerfile`、`etc/`、`.cursor/rules/`、`.agents/skills/` 等按项目实际存在选择
2. 若用户提供参考 `arch.md`：
   - 只抽取章节结构、覆盖面、元信息写法、图表层次
   - 明确过滤参考项目的名称、技术栈、进程、路由、PRD ID、规则路径、部署事实
3. 提议目标项目架构文档目录，一次向用户确认一个核心不确定点：
   - 系统定位与**生产**部署形态（缩小范围 ≠ 降低组件真实性）
   - 技术栈与已定/待定边界
   - 进程/服务/模块边界（禁止把 mock 适配器画成正式模块）
   - 请求路径与数据路径（端到端真实依赖）
   - 配置、存储、队列、缓存、外部依赖（含契约、超时、重试、幂等）
   - 安全、观测、部署、演进路线（演进 = 扩真实能力，不是换掉假实现）
4. 可做有界代码扫描补架构事实：
   - 优先读入口、配置、路由、模块目录，不做全仓逐文件阅读
   - 若扫到非测试 stub/mock/假成功 → 记入「待清除债务」，**不得**合理化进目标架构
   - 发现不确定事实时标 `（待确认）`，不得臆造
5. 写入前展示完整章节预览，用户确认后写入 `docs/arch.md`

## 重复执行（arch.md 已存在）

1. 读现有 `docs/arch.md`，对照 README、PRD、代码入口、配置和最近提交
2. 按「质量评分」给出现状分数、扣分原因、漂移风险
3. 列出疑似问题：
   - 技术栈与依赖文件不一致
   - 架构图缺少新模块或仍保留已删除模块
   - 请求路径、配置路径、部署进程与代码现状冲突
   - 安全/权限/审计要求与 PRD 或 goal 不一致
   - 关键决策没有原因、状态或影响范围
   - **正式组件/路径中出现 stub、mock、假服务、demo 拓扑、MVP 措辞**
4. 逐条向用户确认修订（一次一条）
5. 汇总修订摘要与章节预览，用户确认后最小修改
6. 修订后更新元信息中的 `last_updated`，必要时追加「关键决策记录」条目

## 推荐产出结构

节标题可按项目调整，但首次生成默认使用：

````markdown
# <项目名> — 架构文档

```yaml
version: 0.1.0
last_updated: YYYY-MM-DD
status: draft | planned | active
goal_ref: docs/automate/goal.md
prd_ref: docs/automate/prd.md
rules_ref: <按项目实际填写或 none>
posture: production   # 禁止 demo/mvp 作为 status 替代
```

> 本文档记录技术架构与关键决策，不替代 docs/automate/prd.md 的功能真理源。
> 约束：正式路径禁止 stub/mock 假服务与假绿；测试双不进入架构图。

## 1. 定位
## 2. 技术栈
## 3. 发布与部署策略
## 4. 系统架构
## 5. 请求路径
## 6. 模块边界
## 7. 数据、存储与配置
## 8. 外部依赖与集成契约
## 9. 安全、权限与审计
## 10. 可观测性与运维
## 11. 架构决策记录
## 12. 演进路线与待确认项
## 13. 已知债务（若有 stub/假绿，仅登记清除计划，不得标为目标态）
````

「## 8. 外部依赖与集成契约」至少写清：依赖方、协议、认证、超时/重试、失败语义、数据归属。无外部依赖则写「无」并说明理由。

「## 13. 已知债务」仅当代码里已存在非测试 stub/假绿时使用：登记位置 + 清除条件；**禁止**把债务写成推荐架构。

## 交互式引导问题库

按需使用，一次只问一个：

| 场景 | 问题 |
|------|------|
| 定位不清 | “这个系统更像模块化单体，还是多进程/多服务生产系统？首版范围可以小，但组件是否全部按生产真实依赖设计？” |
| 技术栈待定 | “这项技术是已经在代码里落地，还是目标态选择？是否准备用 mock 顶替真实依赖？”（后者 → 拒绝） |
| 部署边界 | “首版部署实例数可以少，但单实例是否仍按生产配置、观测、密钥与失败模式设计？” |
| 模块边界 | “这个能力应该归入现有模块，还是作为独立边界记录？有没有占位适配器被误当成正式模块？” |
| 请求路径 | “用户触发后，端到端每一跳的真实组件是什么？哪一跳目前是 stub？”（有 stub → 标债务或缩小宣称） |
| 数据归属 | “这类数据的真理源是数据库、对象存储、外部系统，还是配置文件？” |
| 集成契约 | “该外部依赖不可用时，系统应失败、重试还是降级？降级是否仍返回‘成功’假绿？”（假绿 → 禁止） |
| 安全约束 | “这里需要权限、审计、密钥保护、还是合规留痕？” |
| 决策取舍 | “这个选型主要为了可维护性、性能、私有化部署、还是团队熟悉度？（交付速度不能成为引入假服务的理由）” |

## 红线

- 写入前必须展示预览并获得用户确认
- **禁止**把参考 `arch.md` 的项目事实复制到当前项目
- **禁止**在 `docs/arch.md` 新增未经用户确认的产品需求；需求事实应进入 PRD
- **禁止**改 `goal.md`、`prd.md`、`plan.md`；发现不一致只提示对应 skill 处理
- **禁止**演化流程调用本 skill
- **禁止**将 stub / mock 假服务 / 假绿路径 / MVP·demo 拓扑写为目标架构或正式请求路径
- 不确定的架构事实必须标注 `（待确认）`，不得臆造
- 代码中已有假实现 → 只能进「已知债务」并推动清除，不得合理化
